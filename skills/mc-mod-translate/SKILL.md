# Minecraft 模组汉化

把模组 jar 里的 `assets/<ns>/lang/en_us.json` 翻成简体中文 `zh_cn.json`，最终打包成**资源包 zip**交给用户。

**交付形态固定为资源包**：原 jar 不重打包、不覆盖、不替换。用户把资源包丢进 `resourcepacks/` 启用即可。

**产物只留在工作目录 `out/` 下**，汇报里给绝对路径即可。不要额外拷贝到桌面或其他位置。

**核心约束：只翻译字符串值。键名、键序、缩进、换行、转义、颜色码、占位符一律原样保留。**

## 工具链

脚本 `scripts/mct.py`（纯标准库 Python 3.12，无需安装依赖）。下表中 `$M` 代表 `scripts/mct.py` 的绝对路径，`$G` 代表 `--glossary-home "<此处的绝对路径>\glossary"`；**这两处路径一律用 skill 工具报告的本 skill Base directory 拼接**，不要猜。

**在 DSH Windows 沙箱里，PowerShell 不能用 `&` 给子进程接管道**，必须走随附的运行器：

```powershell
. "<Base directory>\scripts\_run.ps1"
Run-Py "<Base directory>\scripts\mct.py" @('--glossary-home','<Base directory>\glossary','probe','mods/xxx.jar')
```

沙箱外（能直接执行 python）时，等价的 `python mct.py ...` 也能用。

| 命令 | 作用 |
|---|---|
| `probe JAR` | 模组 id / loader / 版本、语言文件清单、可用 locale |
| `extract JAR [--work DIR] [--locale en_us]` | 提取源语言到 `source/`，生成译文骨架到 `target/`；jar 内已有 `zh_cn.json` 时会自动沿用其中译文；**MCreator 生成的模组会自动按键名排序原文**（`--no-sort` 关闭，其他模组可用 `--sort` 强制） |
| `merge JAR... [--namespace NS] [--locale en_us]` | 多个 jar / 内嵌模块（JarJar）的语言文件合并成**一份**再翻译；同名命名空间的条目会合并，键冲突有告警；**合并后按键名排序** |
| `nominal WORK [--min N]` | **译前名词盘点**：高频专名、大写短语、重复英文条目 |
| `keys WORK ...` | 列出待译条目；`--cluster` 按概念簇排序，`--simple` / `--complex` 按难度分层，`--min-chars N` 只列长句 |
| `keys WORK --terms` | 追加术语提示列 |
| `glossary lookup "Iron Gear"` | 查整串记忆 + 术语拆解 |
| `glossary search 齿轮` | 模糊查词 |
| `glossary qa --key K --en "英文"` | 查与这条 key 相关的官方 QA 规则 |
| `apply WORK FILE.json` | 把 `{key: 译文}` 合并进译文文件 |
| `apply WORK FILE.json --by-en` | 文件是 `{英文: 译文}`，套用到所有同英文的键（**同一句英文只翻一次**） |
| `check WORK` | 校验；**退出码 0 才算通过**，错误明细写 `report.json` |
| `fmt WORK` | 按源文件的缩进 / 换行 / 键序重排译文 |
| `audit WORK` | 复查 `reference/` 里的旧译文：检出**整段错位**、与术语库冲突的条目；有强错位时退出码 1 |
| `pack WORK` | **产出资源包** `out/<jar名>-zh_cn-resourcepack.zip` |
| `pack WORK --pack-format N` | 手动指定资源包的 `pack_format` |
| `pack WORK --jar` | 额外产覆盖用 jar（**默认不要用**，用户只要资源包） |

工作目录默认 `<当前目录>/.mct/<jar名>/`，结构为 `source/`（原文）、`target/`（译文）、`glossary.json`（项目术语表）、`out/`（产物）。

## 标准流程

0. **probe** 读模组身份：`id`、`loader`、`mc` 版本、语言文件数量与 locale。
   若没有 `en_us` 只有别的语言，用 `--locale <xx_yy>` 指定源语言。
   **联动模组先要本体**：如果这个模组是另一个模组（或系列主模组）的附属，**先向用户要一份被联动模组/主模组的 jar**，用它的 `assets/<ns>/lang/zh_cn.json` 当术语基准。附属模组里的联动条目（方块、材料、机制名）必须和本体官方译名对齐——凭字面翻出来的「马鲁姆/契约/釉面陶瓦」和本体里的「灵灾/条约/漆魂陶瓦」差得很远。
1. **extract** 建工作目录。看输出里的键数和是否存在重复键 / 非字符串值。
   **MCreator 生成的模组**（jar 内有 `net/mcreator/` 类，`probe` 会标 `generator=MCreator`）语言文件键序是随机的，`extract` 会自动按键名排序后再生成骨架——同前缀的条目因此聚成一段，便于审查与分批翻译。别用 `--no-sort` 关掉。
   **模块化的模组**（JarJar 拆成多个 jar、每个 jar 各带一份 `en_us.json`、共用同一个命名空间）必须改用 `merge`：合并成一份再翻，否则资源包里会出现同名的 `zh_cn.json` 互相覆盖。第三方内嵌库（flywheel、ponder 之类）用 `--namespace` 排除或让它自带译名。
   合并时会自动把 jar 内旧版 `zh_cn.json` 写进 `reference/` 并预填骨架，方便核对历史译文。
   **旧译必须先验真**：`extract` / `merge` 发现既有 `zh_cn.json` 时会顺手做一次错位审计，`[warn] 旧译疑似整体错位` 就说明这份译文的值是按别的键序套进去的（模组更新后旧译错位是常见病）。此时用 `audit WORK` 看明细，**清空旧值整体重译**，别照着错位的骨架改——错位是整段的，改一两条没有意义。没有告警也要留意 `[info] 与术语库不符`，那类多半只是命名习惯不同，逐条确认即可。
   **合并结果默认按键名排序**：模块拼接的顺序既不是字母序也不是任何有意义的顺序，排好序才能让人逐段审查、也方便按前缀成组翻译。不要用 `--no-sort` 关掉，除非用户明确要求保留原顺序。
2. **建项目术语表**：读工作目录下的 `glossary.json`，把模组名、核心物品/机制名词填进 `terms`，把品牌名、纯符号放进 `do_not_translate`。这一步决定后面所有条目的一致性。
3. **译前先盘点名词**：`nominal WORK --min 2`。把反复出现的专名（`Buddysteel` 86 次、`Card Stand` 24 次这种）一次性定名写进 `glossary.json` 的 `terms`，重复英文组（`Buddycard Booster Box` 9 次）记下来准备用 `--by-en` 套用。**先定名再翻正文**——命名定完，后面几百条只是套用，返工少一半。
4. **按概念簇、分难度翻译**：
   - `keys --missing --simple --cluster --limit 200`：短名词先做，同一个专名下的条目挨在一起，不会翻到后面忘了前面的用词。
   - `keys --missing --complex --limit 60`：长句/带标点的描述单独一批，慢工细活。
   - 重复英文收进 `{英文: 译文}` 文件，`apply --by-en` 一次铺到所有同英文的键。
   - **长句当场校**：每批里超过 25 字的那几条，写完立刻回头读一遍，别攒到最后。
   - 遇到存疑条目先按「存疑条目」那节攒成选项清单，一次问清再落笔。
5. **check** 修到 0 错误。错误必须逐条修，不许 `--ignore-order` 糊过去。
6. **通顺度校对**：check 通过之后、打包之前，把长句通读一遍按中文语感重写；拿不准的先列出来问用户。
7. **fmt** 兜底重排（apply 已经保序，fmt 是第二道保险）。
8. **pack** 产出资源包。**不要加 `--jar`**，除非用户明确要求覆盖原 jar。
9. 汇报：翻译条数、复用的既有译文、术语表内容、资源包绝对路径、`pack_format` 取自哪个 MC 版本。
   **产物留在工作区即可，不要往桌面或其他目录拷贝一份。**

## 铁律

1. 键名一个字符都不改；不增、不删、不重排键。
2. 占位符与格式码逐字保留：`%s`、`%d`、`%1$s`、`%2$.1f`、`%%`、`§6`…`§r`、`\n`、`\t`、`{0}`、`${...}`、`<br>`。
   - 原文是 `%s` 这种**无序号**占位符时，**不许调换参数顺序**（改成 `%1$s` 会改变格式化行为）；原文已经是 `%1$s` 时才可以自由换位。
3. 不翻译的项：模组名 / 品牌名、纯数字与符号、URL、作者名、`do_not_translate` 里的内容。
4. 除上述白名单外，不允许出现"译文等于原文"。
5. `check` 有错误不得交付。
6. **不重打包 jar**：交付物只有资源包，原 jar 一个字节都不动。
7. **不额外拷贝产物**：资源包只留在工作目录 `out/` 下，不要同步到桌面、`mods/`、`resourcepacks/` 或其他位置。
8. 拿不准的术语先查证，再落笔；查不到就在汇报里列为"待确认"，不要臆造。
9. **不擅自改术语表和词典**：任何增、删、改都要先给变更清单、经用户确认后才落盘。

## 通顺度校对

`check` 只保证格式不错、信息不丢，**不保证读起来像中文**。check 通过之后必须再做一遍通顺度校对。

**范围**：25 字以上的句子、带从句的长句、tooltip 的 behaviour / action 段、ponder 正文、进度描述、配置说明。

**常见病灶与改法**：

| 病灶 | 例子 | 改成 |
|---|---|---|
| 定语堆叠 | 它之后搭建的所有部分都会随关节一起转动 | 在它之后搭建的部分也会跟着转 |
| 照搬外语句式 | 转轴是它朝向的方向 | 绕自身朝向转动 |
| 指代不清 | 把控制台绑定到该步行机：之后**它**能在任何地方操控这台步行机 | ……之后在任何地方都能操控它 |
| 名词化 | 进行组装 / 进行设置 | 组装 / 设置 |
| 空转短语 | 它之后的一切 / ……的情况 | 删掉或换成具体名词 |
| 连续三个「的」 | 步行机的重量和它的动作的增长 | 拆句 |
| 生硬搭配 | 最费应力 / 走过天花板 | 最耗应力 / 沿天花板行走 |

**硬约束**：

- 只调语序和用词，**不增加、不删减信息**
- 改完必须重跑 `check`，确认占位符、`_下划线_`、`§` 一个没动
- 拿不准的改写先列出来问用户，不要自己拍板
- 短名词（物品名、按钮、字幕）不在此列，逐字对应即可

## 翻译阶段的纪律

**先盘点再动笔** —— `nominal` 列出高频专名与重复条目。专名一次定完写进 `glossary.json` 的 `terms`，重复英文用 `apply --by-en` 一次铺开。逐条即兴命名是后面返工的根源。

**按概念簇翻** —— `keys --cluster` 让同一个专名下的方块、物品、卡牌、文本聚在一起。别按 `block.*` / `item.*` 的前缀顺序翻：`Luminis Ore` 在 block、`Luminis Ingot` 在 item、`Luminis Ring` 在 curios，隔着几百行，翻到后面就忘了前面的用词。

**分难度** —— 短名词（无标点、≤6 词）批量做，长句单独一批慢慢来。混装时注意力被简单条目摊薄，长句质量下滑。

**长句当场校** —— 每批写完就回头读超过 25 字的那几条，不要攒到最后一遍再读书。攒到最后时体力已经耗尽。

**长度预算** —— GUI、按钮、菜单、标签的宽度有限。`check` 的 `length` 警告指中文比英文长出一截，看到就压缩，宁可意译短一点。

**中英混排加空格** —— 中文与拉丁字母/数字之间一个半角空格（`已储存 64 FE`、`按住 Shift 右键`）。`check` 的 `cjk-space` 警告指出漏掉的。例外：名字以单个字母结尾时（`迷你T`、`三S`）不加。

**梗要留档** —— 双关、谐音、语气梗译完记进 `glossary.json` 的 `pun`：

```json
"pun": {
  "Groovy": "时髦划丽 —— 谐「华丽」，同时点出「划」凹槽的动作",
  "Flint and Pewter": "打烟石 —— 仿「打火石」，pewter 是锡镴",
  "Garglin' Water": "兽口水 —— 谐「漱口水」，gargoyle + 漱口"
}
```

`check` 会统计 `pun` 条数。汇报时说明哪些梗保住了、哪些只能丢掉——这是译者该交付的信息，不是隐藏成本。

## 存疑条目：给选项，让用户决定

遇到下面这些情况，**不要自己拍板**，要停下来给用户 2–4 个选项：

- 中文社区没有统一说法，或直觉译法与现实行业术语冲突
- 涉及现实行业术语（过山车、铁路、航空、医学、建筑等），存在更规范的现成译法
- 同一英文词在模组里有多种含义（如 `Track` 既可指轨道也可指音轨）
- 品牌名是否翻译、缩写是否展开、音译还是意译
- 一个梗、双关、语气词，需要取舍

输出格式：

```
英文原文 · 出现位置（哪几条 key）

A. 译法 —— 依据/出处；优点；缺点
B. 译法 —— ……
C. 译法 —— ……
推荐 A，因为……

你选哪个？
```

规则：

- 每个选项都要写清**依据**（行业标准、官方译法、社区惯例、专利/文献），不能只凭语感
- 标出推荐项并说明理由，但最终由用户决定
- 用户没回复前不要先改译文；一次攒齐多个存疑条目一起问，不要逐条打断
- 用户选定后写进项目 `glossary.json`，全文件统一

## 术语库改动：先确认再落盘

术语表和词典是这套模式的地基。**任何写操作之前，先把变更清单交给用户确认**，覆盖：

- 项目 `glossary.json` 里 `terms` / `do_not_translate` 的增、删、改
- 内置术语库 `glossary/raw/` 的数据刷新（重下 CFPA / i18n-Dict 数据）
- `glossary build` 重建索引、手工往索引里补词条

清单格式：

```
操作：新增 / 修改 / 删除
条目：<英文> -> <中文>
位置：项目术语表 glossary.json  /  内置术语库 glossary/index
理由：……
影响：会新增/减少多少条强制校验，可能产生哪些误报
```

确认前不要落盘。**即使术语是用户当场选定的，也要走这一步**——写进 `terms` 等于让 `check` 对后续所有条目强制校验，可能带来新的误报，值得先看一眼影响面。

`check` 的警告只用于提示，**不要为了消警告而随手改术语表**。
## 翻译规范速查

- **物品/方块名**：名词短语，不加量词、不加句号。`Iron Gear` → `铁齿轮`，`Energy Cell` → `能量单元`。
- **定语「的」**：只有对比/修饰关系必需时才加。`Deepslate Iron Ore` → `深层铁矿石`（不是"深板岩的铁矿石"）。
- **提示与说明**：保留原文语气，用全角标点 `，。：；！？（）`；引号用 `“”`，书名号/专名用 `《》`。
- **音效字幕** `subtitles.*`：`<主体>：<动作>`。`Block broken` → `方块：被破坏`。
- **进度** `advancements.*.title` 简短短语，`.description` 完整句。
- **GUI/配置**：短、直译、不加多余标点；按钮文字不带句号。
- **中英混排**：中文与英文/数字之间加半角空格（`已储存 64 FE`）；单位不译。
- 完整规则见 `references/translation-rules.md`。

## 术语来源（按优先级）

1. 本模组 jar 内已有的 `zh_cn.json`（extract 已自动沿用）。
2. 项目 `glossary.json` 里已定下的译法。
3. 内置术语库（`glossary` 命令）：CFPA 原版术语表、原版语言记忆库（8560 条 en→zh 对照）、模组翻译指南、i18n-Dict 词典（约 40 万条）。上游地址与更新流程见 `references/glossary-sources.md`。
4. 官方中文 Wiki、MC 百科、模组作者仓库里的 zh_cn。
5. 网络检索确认后写入 `glossary.json`，后续条目复用。

术语库**不自动更新**：只有用户明确说「更新术语库」时才走 `references/glossary-sources.md` 的流程，并且先给变更清单。

同一条英文术语必须全文件同一译法，`check` 会对术语一致性和"未使用术语"报警。

## 自检清单

- [ ] `check` 退出码 0，且没有 `untranslated` / `format` / `key_order` / `missing_key` / `extra_key`
- [ ] `identical` 警告全部在 `do_not_translate` 白名单内
- [ ] `term` / `term_inconsistent` 警告已逐条确认
- [ ] `fmt` 跑过，`report.json` 无键序告警
- [ ] 长句已做通顺度校对，读起来不拗口、不像是外语句式硬搬
- [ ] `pack` 只产出资源包（没有生成 jar）
- [ ] 产物只在工作目录 `out/` 下，没有额外拷贝到桌面或其他位置
- [ ] 术语表 / 词典没有任何未经用户确认的增删改
- [ ] 资源包内 `assets/<ns>/lang/zh_cn.json` 数量与源语言文件数量一致
- [ ] 汇报里给出资源包绝对路径与 `pack_format`
